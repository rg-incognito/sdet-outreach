# SDETOutreach

Finds LinkedIn posts asking Automation Test Engineer / SDET candidates to send their
resume, and automatically emails a personalized outreach message with your resume
attached. Fully local, single command end to end, backed by a local Excel file — no
cloud services beyond the Gemini and Gmail APIs.

```
npm run run-all              # scrape LinkedIn -> tailor -> send, all in one run
npm run run-all -- --dry-run # same, but only logs what would send - no real email
```

Under the hood this is two steps run back to back in one process:

1. **Scrape** — searches LinkedIn's post/content feed with two boolean queries and
   writes every result with a usable recruiter email to the **Posts** sheet inside
   `data/tracker.xlsx`. Must run on this PC — LinkedIn needs the local login session and
   a residential IP.
2. **AI outreach + send** — reads the Posts sheet, skips any recruiter email whose latest
   Tracker row is already `Sent`, scores your resume against the post's keywords,
   generates a personalized outreach email via Gemini, and **automatically emails the
   recruiter with your original resume file attached, unmodified**.

You can also run either half on its own: `npm run scrape-to-sheet` (scrape only) or
`node dist/index.js [--dry-run]` (send only, after a build).

## Search queries

Both are run as full LinkedIn content-search boolean expressions (`config.json` →
`search.queries`):

1. `("Automation Test Engineer" OR SDET) AND ("send resume" OR "email resume" OR "share your CV" OR "mail your CV")`
2. `("Automation Test Engineer" OR SDET) ("careers@" OR "hr@" OR "recruitment@" OR "talent@" OR "jobs@")`

Edit `config.json` → `search.queries` directly to change these (they're full query
strings, not templated from a role-keyword list). `search.maxJobsPerRun` (currently 50)
caps the total posts pulled per run across both queries combined; `src/scrapers/linkedin.ts`'s
`MAX_LOAD_MORE_ATTEMPTS` controls how many scroll cycles it'll do per query to try to
reach that count (LinkedIn's content search is infinite-scroll, not real pagination, so
this is the closest equivalent to "how many pages deep to go").

## The Tracker sheet: full record + automatic retry of failures

`data/tracker.xlsx` has two sheets:

- **Posts** — raw scrape output (Scraped At, Title, Company, Recruiter Email,
  Description, Job URL), deduped by Job URL. This is the input queue.
- **Tracker** — one row per recruiter email, covering every attempt end to end: `Last
  Updated`, `Status` (`Sent` / `Failed`), `Job Title`, `Company`, `Recruiter Email`,
  `ATS Score`, `Subject`, `Body` (the actual Gemini-generated email — not just a log
  line), `Error`, `Job URL`, `Description`. Everything from the original post to the
  exact email that was (or would have been) sent lives in this one row.

If a send fails partway (Gemini error, Gmail auth issue, network blip, etc.), the row is
still written with `Status = Failed`, the error message, and whatever subject/body was
generated before the failure — nothing is silently lost. Only emails whose **current**
row says `Status = Sent` are skipped on the next run; a `Failed` row is retried
automatically next time `run-all` (or the send step alone) runs. A later successful retry
**updates that same row in place** rather than adding a duplicate, so the sheet always
shows current status per recruiter, not a growing log of attempts.

Open `data/tracker.xlsx` directly in Excel any time to review it. Close it before a
scheduled run tries to write to it — a locked/open file will fail that run's write (logged
loudly as an ERROR, since it means that recruiter's status wasn't recorded).

## Outreach emails

Generated by Gemini per recruiter (`src/gemini/generateOutreach.ts`): references the
exact role/company from the post, works in 2-3 of the candidate's actual matched skills,
and signs off with `candidateName` followed by `candidatePhone` on its own line (both
from `config.json`) — no email address in the body, since the message itself is already
from that address. No bracketed placeholders are ever allowed in the output (e.g.
`[Recruiter Name]`) — the prompt explicitly forbids them and instructs the model to write
around unknown details (like the recruiter's actual name) instead.

## Gemini model fallback: tries every callable model, not just one

`src/gemini/client.ts` doesn't just try one fallback model. On any failure — including
`429 RESOURCE_EXHAUSTED` quota errors, which are scoped per-model-per-day and can hit
inconsistently across a key's available models — it walks a whole chain:

1. `GEMINI_MODEL` env override (default `gemini-flash-lite-latest`)
2. `GEMINI_FALLBACK_MODEL` env override (default `gemini-flash-latest`)
3. Every other model this API key can call `generateContent` on, discovered via
   `ai.models.list()` and cached for the process, ordered cheapest/fastest-first
   (flash-lite → flash → pro → everything else)

Only throws once every model in the chain has failed. Each attempt logs which model
failed and which one it's trying next; confirmed in practice against real quota
exhaustion on this key (two `2.0-flash-lite` variants both hit `RESOURCE_EXHAUSTED` before
falling through to a working model).

## Why Excel instead of Google Sheets

Google Sheets is a cloud API — that's what lets JobMailer (this project's sibling) run
its send step on a GitHub Actions hosted runner while scraping stays local. A local
`.xlsx` file only exists on this PC's disk, so a hosted runner can't reach it. That's why
this project runs entirely locally — one scheduled task, no GitHub Actions — and sends
only go out while this PC is on and logged in.

## One-time setup

1. **Install dependencies**:
   ```
   npm install
   npx playwright install chromium
   ```

2. **Fill in `.env`** (copy `.env.example` → `.env` first):
   - `GEMINI_API_KEY` — from [Google AI Studio](https://aistudio.google.com/apikey).
   - `GMAIL_USER` — the Gmail address sends will come from.
   - `GMAIL_APP_PASSWORD` — enable 2-Step Verification on that Gmail account
     (https://myaccount.google.com/security), then generate an App Password
     (https://myaccount.google.com/apppasswords) and paste the 16-character password here
     (no spaces).

3. **Master resume**: put your resume file in this folder and update `config.json`:
   - `masterResumePath` — e.g. `"My_Resume.pdf"` (`.md`/`.txt`/`.docx`/`.pdf` all
     supported; only a `.pdf` source is attached verbatim byte-for-byte, others are
     rendered to PDF via `src/resume/renderPdf.ts` with unmodified content).
   - `candidateName` — drives the sign-off name on generated outreach emails and the
     attached filename.
   - `candidatePhone` — appears on the line right after `candidateName` in every
     generated email's sign-off. Leave as `""` to omit it (falls back to name-only
     sign-off).

4. **Log into LinkedIn once** so the scraper can see full post content:
   ```
   npm run linkedin-login
   ```
   A browser window opens — log in manually, then return to the terminal and press Enter.
   This saves a session file to `data/storageState.json` (gitignored, no password
   stored). Re-run this whenever LinkedIn scraping starts failing (session expired, or
   flagged — see "Known limitations" below). Only ever use this session from this one
   PC/IP.

5. **Register the scheduled task** (PowerShell):
   ```
   powershell -ExecutionPolicy Bypass -File scripts/register-task.ps1
   ```
   Fires `npm run run-all` once at logon, then every 2 hours after that, for as long as
   the machine is on and you're logged in.

## Running it day to day

```
npm run run-all -- --dry-run    # safe: logs what would send, no real email, no sheet write
npm run run-all                 # real: scrape, then send to every pending row
```

Check `logs/run-*.log` for how many posts were scraped, how many had a usable email, and
per-recruiter send results. `logs/audit.log` has a durable JSON-lines record of every
real send too.

Scheduled task management:
```
Get-ScheduledTaskInfo -TaskName SDETOutreachRunAll     # last run time/result
Start-ScheduledTask -TaskName SDETOutreachRunAll       # run immediately
Unregister-ScheduledTask -TaskName SDETOutreachRunAll -Confirm:$false   # remove it
```

## Known limitations (read before relying on this)

- **LinkedIn sessions get flagged when reused from a different IP/location.** If a run
  logs "no posts found" along with a `landed on "Loading .../checkpoint/..."` line, the
  session needs a fresh `npm run linkedin-login`.
- **LinkedIn searches its post/content feed, not Jobs listings** — hiring/ask posts in the
  feed frequently include a real contact email (LinkedIn auto-linkifies these as
  `mailto:` links, or the email is just typed in visible text, both of which the scraper
  reads), unlike formal Jobs listings which almost never do. LinkedIn prohibits automated
  scraping in its Terms of Service. Selectors are best-effort and will break when LinkedIn
  changes its markup. No stealth/anti-detection/CAPTCHA-solving is implemented; a block
  just means 0 results without crashing the script.
- **LinkedIn's content search is infinite-scroll, not real pagination.** Raising
  `maxJobsPerRun` makes the scraper scroll further per query (bounded by
  `MAX_LOAD_MORE_ATTEMPTS`), not fetch additional "pages" in the traditional sense. Higher
  values mean noticeably longer runs (more scrolling, more per-post delay).
- **The resume itself is never rewritten by AI.** Only the outreach email copy is
  AI-generated; the attachment is always your original `masterResumePath` file, read and
  attached verbatim (byte-for-byte if it's already a `.pdf`).
- **Known non-recruiting mailboxes are filtered out** before reaching the Posts sheet —
  `src/utils/isGenericMailbox.ts` blocklists things like ADA accommodation lines,
  employee-relations, legal/compliance, support/noreply, etc.
- **India-located posts are filtered out** — `src/utils/isIndianLocation.ts` checks the
  post body text for India city/region names. Delete this filter call in
  `src/scrapeToPosts.ts` if you don't want it.
- **Emails send automatically with no human review step.** Every real send is appended to
  `logs/audit.log` and reflected in the Tracker sheet, since this is otherwise
  irreversible. Use `--dry-run` liberally when testing changes.
- **Dedup is by recruiter email, not by posting** — if the same email shows up from two
  different posts, only the first `Sent` row ever gets created for it; later posts with
  that same email are skipped as already contacted.
- **Gemini quota errors are handled by trying every callable model** for the key (see
  above) before giving up — but if every model on the key is exhausted for the day, the
  run still fails for that post and gets retried (Tracker `Status = Failed`) next time.

## Project layout

- `src/scrapers/linkedin.ts` — runs both configured boolean queries against LinkedIn's
  content search, scroll-paginating and extracting post text + any mailto emails
- `src/scrapeToPosts.ts` — shared scrape → filter → Posts-sheet logic used by both
  `scripts/scrape-to-sheet.ts` and `scripts/run-all.ts`
- `src/filters/extractEmail.ts` — pulls a single usable email out of a post's text
- `src/utils/isGenericMailbox.ts` — blocklist for non-recruiting mailbox patterns
- `src/utils/isIndianLocation.ts` — drops India-located posts
- `src/excel/` — `workbook.ts` (shared `data/tracker.xlsx` load/save), `postsSheet.ts`
  (raw scrape output, deduped by post URL), `trackerSheet.ts` (one row per recruiter
  email, upserted; `Status: Sent` is the only thing that blocks a retry)
- `src/emailJob.ts` — scoring/attach/send logic; catches failures internally and always
  writes a Tracker row (`Sent` or `Failed`) with whatever was generated
- `src/pipeline.ts` — reads Posts sheet, dedups against Tracker sheet, tailors + sends
- `src/resume/` — resume loading, ATS keyword scoring, PDF rendering (no AI rewriting)
- `src/gemini/` — `client.ts` (multi-model fallback chain), `extractSkills.ts` (JD
  keyword extraction), `generateOutreach.ts` (outreach email generation, name+phone
  sign-off)
- `src/mailer/sendMail.ts` — Gmail SMTP sending (no-op under `--dry-run`)
- `src/store/auditLog.ts` — local audit log (`logs/audit.log`)
- `src/index.ts` — send-only CLI entry point (`--dry-run`)
- `scripts/run-all.ts` — complete local run: scrape then send, one process
- `scripts/scrape-to-sheet.ts` — scrape-only CLI
- `scripts/linkedin-login.ts` — one-time interactive LinkedIn login
- `scripts/register-task.ps1` — single Windows Scheduled Task (`npm run run-all`, logon +
  every 2h)

## Config reference (`config.json`)

| Field | Meaning |
|---|---|
| `search.queries` | Array of full LinkedIn content-search boolean query strings, each run as its own search |
| `search.maxJobsPerRun` | Total posts to scrape per run, across both queries combined |
| `search.regionGeoUrn` | Optional LinkedIn geoUrn for a region facet on the search (empty = no region filter) |
| `sources.linkedin.storageStatePath` | Path to the saved LinkedIn session (`data/storageState.json`) |
| `masterResumePath` | Path to the resume file attached to every send |
| `candidateName` | Sign-off name in generated emails, and the attached filename |
| `candidatePhone` | Sign-off phone number, on the line after `candidateName` (omit sign-off line if empty) |

## Environment reference (`.env`)

| Var | Required | Purpose |
|---|---|---|
| `GEMINI_API_KEY` | Yes | Gemini API key (Google AI Studio) |
| `GMAIL_USER` | Yes | Gmail address sends come from |
| `GMAIL_APP_PASSWORD` | Only for real sends | 16-char Gmail App Password; `--dry-run` works without it |
| `GEMINI_MODEL` | No | Overrides the primary model (default `gemini-flash-lite-latest`) |
| `GEMINI_FALLBACK_MODEL` | No | Overrides the second model tried (default `gemini-flash-latest`) |
